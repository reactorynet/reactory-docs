# Internationalisation (i18n)

Reactory renders user-facing text in the language the user chose, on both the
server and the client. This page documents the moving parts, the rules that are
enforced by tests and scripts, and the conventions new code must follow.

## Where translations live

| Layer | Location | Authority |
| --- | --- | --- |
| `module` | translations compiled into a module (`module.translations`) | lowest |
| `file` | `reactory-data/i18n/<locale>/<namespace>.json` | middle |
| `cms` | rows written by `ReactorySetTranslation` (the StaticContent panel) | highest |

**Precedence is `module` → `file` → `cms`; later layers win.** The order is
implemented once, in
`reactory-express-server/src/express/i18n/translationLayers.ts`
(`resolveTranslationBundle`), and asserted in
`src/express/i18n/__tests__/translationLayers.test.ts`.

This matters: before it was made explicit, both `TranslationService.getTranslations`
and the `ReactoryTranslation` resolver spread the JSON bundle *over* the merged
result, so a string committed to a file silently shadowed a CMS edit. An editor
could fix a typo, see it in the panel, and have the site keep serving the old
text with nothing in the logs.

Two consequences worth remembering:

* a `null`/`undefined` value in a higher layer is **not** an override — an empty
  CMS row must not blank a shipped string; and
* a *deliberately* empty string **is** an override (an editor cleared the field).

## Locale folders are the source of truth

`reactory-data/i18n/<locale>/<namespace>.json`. The server derives the selectable
language list from the folders on disk (`getAvailableLanguages`), so **adding a
folder is all that is required** to offer a new language — there is no hardcoded
list on either side, and `bin/utils/build/package-translations.ts` discovers
locales the same way.

A language *code* is the stable identity (`af`), while a *folder* is a storage
detail (`af`, or `en-US`). `resolveLocaleFolder` maps one onto the other. Codes
are always normalised to their lowercase primary subtag; a regional tag
(`af-ZA`) therefore resolves to `af`.

Every namespace file in `i18n/` is tracked in git. Ignore the generated
artefacts by name (`*.missing.json`, `*.tmp`), never the whole directory — git
does not descend into an ignored directory, so a `!i18n/*/file.json`
re-include inside one can never match.

## Writing translatable strings

### Server

```ts
// inside a resolver/service with a request context
context.i18n.t('support-ticket.model.status.open')
```

`ReactoryContext` resolves the request language from the `x-reactory-language`
header (preferring it over `Accept-Language`) and gives each request its own
cloned i18next instance, so one caller's `changeLanguage` cannot change what
another caller renders.

### Client

```tsx
const { t } = useTranslation();
return <p>{t('reactor.client.chat.noContent')}</p>;
```

Add the key to **every** shipped locale, not just `en`.

### Guard

`reactory-pwa-client/scripts/i18n/check-jsx-literals.mjs` (run with
`yarn lint:i18n`) parses every JSX file with the TypeScript compiler and fails on
a hardcoded text literal or a text-bearing attribute (`label`, `title`,
`placeholder`, `alt`, `aria-label`, `helperText`, `tooltip`) that is not in
`scripts/i18n/jsx-literal-baseline.json`.

The baseline is a **ratchet**, not a permanent excuse: existing literals are
grandfathered so the extraction work can land incrementally, but no new one can
be added. Run `yarn lint:i18n -- --update` after extracting strings, and commit
the shrunken baseline.

## Plurals

i18next selects a plural form from an option named `count`. A key whose text
interpolates `{{count}}` **must** ship `_one` and `_other` (plus the
language-specific forms a locale needs — `_few`, `_many`):

```json
{
  "reactor.client.chat.toolResultsSummary_one": "Completed {{count}} tool call",
  "reactor.client.chat.toolResultsSummary_other": "Completed {{count}} tool calls"
}
```

```tsx
t('reactor.client.chat.toolResultsSummary', { count: results.length })
```

Without the plural forms English renders *"1 tool calls"*; without the `count`
option i18next always picks `_other`. `{{selected.length}}` cannot drive plural
selection at all — pass a separate `count`.

`bin/scripts/i18n-check-parity.sh` fails on a count-bearing key with no plural
pair, and flags any interpolation of an array `.length` (which needs a `count`
option at the call site first).

## Dates and numbers

Use `reactory-pwa-client/src/api/formatters.ts`:

```ts
import { formatDate, formatNumber, formatMoment } from '@reactory/client-core/api/formatters';

formatDate(order.createdAt);           // follows the selected language
formatNumber(total, { style: 'currency', currency: 'ZAR' });
formatMoment(order.createdAt, 'LLLL'); // moment, with its locale registered
```

Do **not** call `toLocaleDateString()` / `Intl.NumberFormat` without an explicit
locale, and do not rely on `moment`'s default locale: both follow the *browser*
locale, which disagrees with the app language when the user picks a language
different from their OS. The formatters take the active language explicitly,
defaulting to the App default (never the browser).

`registerMomentLocale` is called by `ReactoryApi` on start-up and on every
language switch, so moment's month names follow the UI.

## User language preference

Resolution order on start-up:

1. this device's explicit choice (`localStorage['$reactory$language']`);
2. the account's persisted preference (`user.il8n.locale`);
3. the first browser language that is supported;
4. the application default.

`setLanguage` writes to all of the above: `localStorage` immediately (the UI
must not wait on a network round trip) and the account via the
`setUserLanguage` mutation, fire-and-forget. A failure degrades to per-device
behaviour rather than blocking the switch.

Only a language the server actually ships may be **stored**; `setUserLanguage`
rejects anything else rather than storing a locale with no bundles, which would
silently pin the account to English forever.

**Reading** deliberately does not re-check the on-disk list. What a process
happens to have mounted is not a property of the account: a deployment without
the data volume, a cold start before the locale tree is read, or a CI checkout
with no `i18n/` directory would each silently render every user in English while
their preference sat there looking correct. A missing bundle is handled per key
by `fallbackLng`, so resolution returns the stored language and lets the fallback
do its job. Only a structurally implausible value is discarded.

Writes validate, reads trust — that asymmetry is intentional and each half is
covered by a test (`utils/userLanguage`).

## Transactional email

Emails are asynchronous, so the language comes from the **recipient**
(`user.il8n.locale`) — not from the request that triggered the send. A support
agent resending an activation email is not the person who will read it.

```ts
const translator = await createEmailTranslator(recipient);
const properties = emailTemplateProperties(translator, { partner, user });
```

Templates receive `t`, `locale` and `dir` (so an RTL locale can set the document
direction). Strings live in `i18n/<locale>/emails.json`.

## What is not supported yet

* **RTL layout.** `dir` is emitted for email and `languageDirection()` reports
  the direction, but no client layout pass exists, so Arabic/Hebrew would render
  mirrored text in a left-to-right layout.
* **Native speaker review.** Machine-drafted translations are marked as such in
  the ticket that tracks them; they are not signed off.
